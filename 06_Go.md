# Go for Backend Engineers

A working guide to Go for people who build and operate backend services. It teaches how the language and runtime behave, so you can write correct concurrent services and diagnose them in production, not just recall syntax.

**Audience:** developers who already know JavaScript/Node and want production-level Go skill.
**Prerequisites:** programming fundamentals, basic HTTP and SQL, and the Linux basics in `03_Linux.md`.
**Scope:** server-side Go: language core, concurrency, standard-library HTTP, JSON, SQL, testing, profiling. GUI, mobile and cgo internals are out of scope.
**Accuracy status:** Reviewed against official documentation on 2026-11-06; items still unverified are marked.
**Note on accuracy:** the language is stable and backward compatible, but the standard library and tooling gain features each release. Where this guide names a feature tied to a specific release, it gives the release. Check the official release notes for the Go version you run. Code snippets are small and meant to be idiomatic, but they were not compiled for this review, so compile them yourself.
**Plain-language aids:** each chapter starts with "In plain words". Hard terms are explained in brackets at first use. Chapter 25 is a glossary.

## How to use this guide

Each chapter has four parts:

1. **Understand**: the concepts and the reasoning behind them.
2. **Tools to master**: what to learn to use fluently, and the level to reach.
3. **Common mistakes**: what goes wrong in practice.
4. **Self-check**: questions you should be able to answer without notes.

Chapter 22 lists hands-on labs. Chapter 23 collects interview questions with model answers. Chapter 24 lists primary references. Chapter 25 is the glossary.

**What "good enough" means for a backend role:** you can write an HTTP service with correct timeouts, cancellation and graceful shutdown; you can reason about goroutine lifetimes and shared state; you can read a race report and a pprof profile; and you can explain why you chose Go (or Node) for a given service. Chapters 6, 7, 10 to 13, 15 and 20 matter most.

## 1. The mental model

**In plain words:** Go builds your code into one program file that you can copy to a server. It can run many tasks at the same time with goroutines [light tasks managed by the Go runtime]. The language is small, so most Go code looks similar.

### Understand

**Compiled, statically typed, garbage collected.** `go build` produces a single native binary, by default statically linked for pure-Go programs. There is no interpreter, no `node_modules` at runtime and no separate runtime to install. Deployment is copying one file into a minimal container image.

**Small language, large standard library.** Go deliberately has few features: no classes, no inheritance, no exceptions for ordinary errors, no operator overloading. The standard library covers HTTP, JSON, SQL interfaces, crypto, testing and profiling. Most Go services need few third-party dependencies, which is a real operational advantage.

**Concurrency is built into the runtime.** A **goroutine** is a function running concurrently, scheduled by the Go runtime onto a small pool of OS threads. Goroutines start with small stacks that grow as needed, so hundreds of thousands are practical. Blocking in Go (a network read, a channel receive, a mutex wait) parks the goroutine and lets the runtime run another. You write straightforward blocking code and get the scalability that Node achieves with callbacks and `async/await`.

**The scheduler (G, M, P).** Goroutines (G) run on OS threads (M), and a processor token (P) is needed to run Go code. The number of Ps defaults to the number of logical CPUs available to the process (`GOMAXPROCS`). From Go 1.25 on Linux it is also lowered to the container's CPU limit. Consequence: unlike Node's single JS thread, one Go process uses all cores, and CPU-bound work does not block other requests. The scheduler is cooperative-plus-preemptive in recent versions, so a tight loop does not starve others, but you should not rely on scheduling details.

**Share memory by communicating, and also by locking.** The proverb says "do not communicate by sharing memory; share memory by communicating". In practice Go code uses both channels and mutexes. Choose the simpler one for the problem (chapter 11).

**Explicit over implicit.** Errors are return values. Dependencies are explicit parameters. Zero values are usable. Formatting is not debated, because `gofmt` decides.

**Value semantics by default.** Assignment and function arguments copy. Structs, arrays and basic types are copied; slices, maps, channels, functions and pointers are small headers or references, so copying them copies the header, not the underlying data. Most Go surprises come from forgetting this.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Reading the docs | `go doc`, `go doc net/http.Server`, pkg.go.dev | Answer API questions without a search engine |
| Scheduler visibility | `GODEBUG=schedtrace=1000`, `runtime.NumGoroutine()`, `runtime/trace` | Know the tools exist and when to use them |
| Runtime knobs | `GOMAXPROCS`, `GOGC`, `GOMEMLIMIT` | Explain what each controls |

### Common mistakes

- Treating goroutines as free. Each has a stack and, more importantly, a lifetime you must manage (chapter 13).
- Writing Go like Java or Node: deep abstractions, premature interfaces, callback-style code.
- Assuming an older Go sees a container's CPU limit. Before Go 1.25, `GOMAXPROCS` defaulted to the host CPU count, which can oversubscribe a CPU-limited container. From Go 1.25 on Linux, the default respects the cgroup CPU bandwidth limit [the CPU quota given to a container]. On older versions, set it explicitly (the `automaxprocs` library is a common remedy).

### Self-check

- What happens to a goroutine that blocks on a network read? What happens to the OS thread?
- Why can one Go process saturate eight cores while a Node process cannot, by default?
- Which Go types are copied by value and which share underlying data when assigned?

## 2. Toolchain and modules

**In plain words:** A module [a project with a `go.mod` file that lists its dependencies] is how Go organises code. The `go` command builds, tests and downloads code for you. This chapter shows the commands you use every day.

### Understand

**Modules.** A module is a tree of packages with a `go.mod` file at its root, declaring the module path, the Go version and dependencies. `go.sum` records cryptographic hashes of dependencies so builds are verifiable. Commit both files. There is no `node_modules` in the repo; modules are downloaded into a shared cache (the module cache).

```
module example.com/orders

go 1.22

require github.com/jackc/pgx/v5 v5.5.5
```

(The versions above are illustrative; use whatever `go get` resolves.)

**Minimal version selection.** Go picks the minimum version satisfying all requirements, not the newest. Builds are reproducible without a lockfile separate from `go.mod`. Upgrades are explicit (`go get pkg@version`, `go get -u`).

**Packages and visibility.** A directory is a package. Identifiers starting with an upper-case letter are exported; lower-case ones are package-private. There are no `public` or `private` keywords. Import cycles are a compile error, which forces clean layering.

**Core commands.**

- `go run .` compiles to a temporary binary and runs it. For development.
- `go build ./...` compiles everything and discards non-main packages. `go build -o bin/api ./cmd/api` writes a binary.
- `go test ./...` runs tests in all packages.
- `go vet ./...` reports suspicious constructs the compiler allows (misused `Printf` verbs, copied locks, unreachable code, some loop-variable mistakes).
- `gofmt` (or `go fmt`) formats code. Run it on save and in CI. `goimports` also manages import lines.
- `go mod tidy` adds missing and removes unused dependencies. Run it before committing.
- `go mod why`, `go list -m all`, `go mod graph` explain why a dependency is present.
- `go install pkg@version` installs a tool binary.

**Cross-compilation.** Set `GOOS` and `GOARCH` (for example `GOOS=linux GOARCH=amd64 go build`). With `CGO_ENABLED=0` the result has no C library dependency, which suits `scratch` or distroless images. Anything using cgo (some DB drivers, `net` with certain resolver settings) needs care; confirm in the docs.

**Build metadata.** Version info is injected at link time with `-ldflags "-X main.version=..."`. `-trimpath` removes local paths from the binary for reproducibility.

**Workspaces.** `go work init ./svc-a ./svc-b` creates a `go.work` file so several modules in a monorepo resolve each other locally during development, without `replace` directives in each `go.mod`. Typically `go.work` is not used for release builds; confirm the team convention.

**Private modules.** `GOPRIVATE` (and `GOPROXY`, `GONOSUMDB`) controls which module paths bypass the public proxy and checksum database. Needed when a repo depends on private code.

**Supply chain.** `govulncheck ./...` reports known vulnerabilities that your code actually reaches. Run it in CI.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Build and run | `go build`, `go run`, `go install`, `-ldflags`, `-trimpath` | Produce a reproducible static binary for a target OS |
| Dependencies | `go mod tidy`, `go get`, `go mod why`, `go list -m -u all`, `go mod vendor` | Add, upgrade, and explain a dependency |
| Formatting and static checks | `gofmt`, `goimports`, `go vet` | Run on every commit |
| Linting | `staticcheck`, `golangci-lint` | Configure a lint set and keep CI green |
| Vulnerabilities | `govulncheck` | Read a report and decide on an upgrade |
| Monorepos | `go work init`, `go work use` | Develop two modules together locally |
| Environment | `go env`, `GOFLAGS`, `GOPROXY`, `GOPRIVATE` | Fix a failing private-module download |

### Common mistakes

- Committing without running `go mod tidy`, leaving `go.mod` and `go.sum` stale.
- Ignoring `go vet` output. Most of it is real bugs.
- Using `replace` directives in committed `go.mod` files for local development instead of a workspace.
- Building on a developer laptop and shipping a binary for the wrong OS or architecture.
- Treating `go run` as the production start command. Ship a built binary.

### Self-check

- What do `go.mod` and `go.sum` each contain, and which must be committed?
- How does Go decide which version of a dependency to use?
- What does `CGO_ENABLED=0` change and why do container images care?
- When would you use a workspace instead of a `replace` directive?

## 3. Types, zero values, strings and runes

**In plain words:** Every Go variable has a type and always has a value. If you do not set it, Go gives it a zero value [the default for that type, such as 0 or an empty string]. A string is a list of bytes, so its length is not always the number of visible characters.

### Understand

**Zero values.** Every variable is initialised. Numbers are `0`, booleans `false`, strings `""`, and pointers, slices, maps, channels, functions and interfaces are `nil`. Good Go design makes the zero value useful: a `sync.Mutex`, `bytes.Buffer` or `sync.WaitGroup` works without a constructor. A key backend consequence: you cannot tell "field absent" from "field zero" in a plain struct field. That matters for JSON and database nulls (chapters 16 and 17); use pointers, `sql.Null*` types or dedicated types when absence is meaningful.

**Declarations.**

```go
var n int            // zero value
count := 3           // short declaration, inside functions only
const Timeout = 5    // untyped constant
```

`:=` declares and assigns; at least one variable on the left must be new. A subtle trap is shadowing: `err :=` inside an inner scope creates a new `err` and the outer one stays unchanged.

**Basic types.** `int` and `uint` are platform sized (64-bit on 64-bit systems). Use explicit sizes (`int64`, `uint32`) for data crossing a process boundary. `float64` is the default float. `byte` is an alias for `uint8`; `rune` is an alias for `int32` holding a Unicode code point. Integer overflow wraps silently; there is no exception. Never use floating point for money; use integer minor units or a decimal library.

**Named types.** `type UserID int64` creates a distinct type. It cannot be mixed with `int64` without a conversion, which catches argument-order bugs. `time.Duration` is the standard example: `5 * time.Second`.

**Strings, bytes, runes.** A Go string is an immutable sequence of bytes, conventionally UTF-8. `len(s)` is the byte count, not the character count. Indexing `s[i]` yields a byte. `for i, r := range s` decodes UTF-8 and yields the byte index and a rune; invalid bytes yield `U+FFFD`.

```go
s := "héllo"
fmt.Println(len(s))                    // 6 bytes
fmt.Println(utf8.RuneCountInString(s)) // 5 runes
for i, r := range s {
    fmt.Println(i, string(r))          // i is a byte offset
}
```

Concatenating in a loop with `+=` copies each time. Use `strings.Builder`. `[]byte(s)` and `string(b)` conversions generally copy. Use the `bytes` package for byte slices and `strings` for strings; their APIs mirror each other.

**Pointers.** `&x` takes an address; `*p` dereferences. There is no pointer arithmetic. Struct field access through a pointer is automatic (`p.Name`). Pointers are used to share mutation, to avoid copying large structs and to represent optional values; they are not needed for every struct.

**Control flow.** `for` is the only loop (`for {}`, `for cond {}`, `for i := 0; i < n; i++ {}`, `for range`). `switch` does not fall through by default. `if v, ok := m[k]; ok {}` is the standard idiom for map lookups. Go 1.22 and later allow `for i := range 10`.

**Loop variables.** Before Go 1.22 a `for` loop declared one variable shared across iterations, so closures and goroutines started in the loop could all observe its final value. From Go 1.22, each iteration has its own copy, controlled by the `go` version line in `go.mod`. If your module declares an older version, the old behaviour applies. State the version when you review code, and do not assume.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Formatting values | `fmt.Printf` verbs `%v %+v %#v %T %q %x`, `%w` in `fmt.Errorf` | Inspect any value and its type quickly |
| Strings | `strings`, `strings.Builder`, `strconv`, `unicode/utf8`, `bytes` | Handle UTF-8 correctly and build strings efficiently |
| Time | `time.Duration`, `time.Now`, `time.Since`, `time.Parse` layout | Use durations, never raw integers for time |
| Numbers | `math`, `math/big`, `strconv.ParseInt` | Parse with bit sizes and handle errors |

### Common mistakes

- Using `len(s)` as a character count for non-ASCII text.
- Shadowing `err` with `:=` in an inner block and then returning the outer, still-nil `err`.
- Using `float64` for currency.
- Parsing numbers with `Atoi` and ignoring the error.
- Assuming a nil map is writable. Reading a nil map is fine; writing panics.

### Self-check

- What does `len("é")` return and why?
- What is the zero value of a slice, a map, an interface and a struct?
- Why can `x := f()` in an inner scope cause a silently ignored error?
- Which loop-variable semantics apply to your module, and where is that decided?

## 4. Slices and maps

**In plain words:** A slice [a view over a list of values stored in an array] is the list type you use most. Two slices can point to the same array, so changing one can change the other. A map [a table of key and value pairs] is not safe to use from many goroutines at once.

### Understand

**Arrays and slices.** An array `[3]int` has a fixed length that is part of its type, and is copied by value. A **slice** is a small struct (a three-word header) of: a pointer to an underlying array, a length `len` and a capacity `cap`. Slices are what you use. Passing a slice to a function copies the header, so the callee sees and can modify the same elements but cannot change the caller's length.

**Append and aliasing.** `append` writes into spare capacity if there is room; otherwise it allocates a bigger array, copies, and returns a header pointing to the new array. You must use the return value.

```go
a := make([]int, 3, 4) // len 3, cap 4
b := append(a, 10)     // fits in capacity: shares a's array
c := append(a, 20)     // also fits: overwrites the same slot
fmt.Println(b[3], c[3]) // 20 20 : b and c alias

d := append(b, 30)     // exceeds cap: new array, no longer aliased
d[0] = 99
fmt.Println(a[0])      // 0
```

The rule: after an `append`, you cannot know whether the result shares memory with the input without knowing the capacity. Functions that append to a slice parameter and return it, and callers that keep both old and new slices, are a classic source of data corruption. Defensive options: return a fresh slice, copy with `copy` or `slices.Clone`, or use a full slice expression `s[low:high:max]` to limit the capacity of a sub-slice so appends reallocate.

**Sub-slices keep the whole array alive.** `small := big[:10]` keeps the entire backing array of `big` reachable. Copy out the part you need if `big` is large and `small` is long-lived. That is a common memory-retention bug when slicing large buffers read from the network.

**Preallocation.** `make([]T, 0, n)` avoids repeated growth when you know `n`. `make([]T, n)` creates `n` zero elements, and a subsequent `append` adds after them: a frequent bug.

**nil versus empty.** A nil slice and an empty slice both have length 0 and work with `append`, `len` and `range`. They differ for `== nil` and in JSON encoding (nil becomes `null`, empty becomes `[]`).

**Maps.** A map is a hash table reference type. `make(map[string]int)` creates one. Behaviours to know:

- Iteration order is unspecified and deliberately randomised between runs. Never depend on it. Sort the keys for deterministic output.
- Reading a missing key returns the zero value; use `v, ok := m[k]` to tell absence from zero.
- Writing to a nil map panics.
- Maps are **not safe for concurrent use**. Concurrent read and write is a data race, and the runtime may detect it and abort the program with a fatal error that cannot be recovered. Guard with a `sync.RWMutex`, confine to one goroutine, or use `sync.Map` for its specific cases (mostly write-once, read-many or disjoint keys).
- Keys must be comparable (`==` defined): not slices, maps or functions. Structs of comparable fields and arrays are fine.
- You may delete entries during a range. Entries added during iteration may or may not be visited.
- Map values are not addressable, so `m[k].field = x` does not compile for struct values. Store pointers or copy, modify and reassign.
- Maps do not shrink their memory when entries are deleted. A map that once held millions of entries keeps its buckets; rebuild it if that matters.

Recent versions add the `slices` and `maps` standard packages (`slices.Sort`, `slices.Contains`, `slices.Clone`, `maps.Keys` and others) and a `clear` builtin. Confirm availability for your Go version.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Inspecting slices | `fmt.Printf("%v len=%d cap=%d")`, `slices` package | Predict `len` and `cap` after each operation |
| Copying | `copy`, `slices.Clone`, full slice expression | Break aliasing deliberately |
| Concurrency on maps | `sync.RWMutex`, `sync.Map`, `go test -race` | Detect and fix a concurrent map access |
| Allocation behaviour | `go test -bench -benchmem`, `go build -gcflags=-m` | See allocations from growth and escapes |

### Common mistakes

- Appending to a sub-slice and overwriting elements of the original.
- Using `make([]T, n)` then `append`, producing `n` leading zeros.
- Keeping a tiny sub-slice of a huge buffer alive.
- Ranging over a map and expecting stable order in a test or an API response.
- Sharing a map between goroutines without a lock.
- Modifying a slice while ranging over it and expecting the range to see the changes. `range` evaluates the slice once.

### Self-check

- What are the three fields of a slice header, and what does passing a slice to a function copy?
- Given `a := make([]int, 3, 4)`, what do `append(a, 1)` and `append(a, 2)` do to each other?
- Why does map iteration order vary, and how do you produce stable output?
- Why can a concurrent map write crash the whole process?

## 5. Structs, methods and embedding

**In plain words:** A struct groups related values under one name. A method is a function attached to a type. Go has no inheritance, but embedding [placing one type inside another] lets you reuse code.

### Understand

**Structs** group fields. Construction uses a composite literal with named fields: `User{ID: 1, Name: "a"}`. Unkeyed literals break when fields are added. Structs are compared with `==` if all fields are comparable.

**Methods** are functions with a receiver: `func (u User) Name() string` (value receiver) or `func (u *User) SetName(n string)` (pointer receiver).

**Value versus pointer receiver.**

- A value receiver gets a copy. Mutations are lost.
- A pointer receiver can mutate and avoids copying large structs.
- Use a pointer receiver if the type contains a `sync.Mutex` or similar (copying a lock is a bug that `go vet` flags), if any method must mutate, or if the struct is large.
- Be consistent: if some methods need a pointer receiver, make all of them pointer receivers.
- The **method set** rule: the method set of `T` contains value-receiver methods; the method set of `*T` contains both. So a `T` value does not satisfy an interface if the interface requires a pointer-receiver method. `var _ I = (*T)(nil)` is a compile-time assertion that `*T` implements `I`.
- Go auto-takes the address for calls on addressable variables (`u.SetName("x")` works on a variable) but not on non-addressable values like map elements.

**Constructors.** Go has no constructors. By convention `NewThing(deps...) (*Thing, error)` validates and returns a ready value. Prefer making the zero value usable when you can. The **functional options** pattern (`NewServer(addr, WithTimeout(d))`) handles many optional settings.

**Embedding.** A struct can embed another type without a field name, promoting its fields and methods.

```go
type Logger struct{ prefix string }
func (l Logger) Log(msg string) { fmt.Println(l.prefix + msg) }

type Service struct {
    Logger          // embedded: Service gets Log
    db *sql.DB
}
```

This is composition with convenient forwarding, not inheritance. There is no polymorphism through embedding: methods of the embedded type see the embedded value, not the outer one. Embedding an interface in a struct is a common test technique (embed the interface, override one method). Embedding exports the embedded type's exported methods on your public type, which widens your API surface. Prefer a named field when you do not want promotion. Embedding `sync.Mutex` publicly exposes `Lock` and `Unlock`; usually a named unexported field `mu sync.Mutex` is better.

**Struct tags** are string metadata read by reflection: `json:"user_id,omitempty"`, `db:"user_id"`. They are not checked by the compiler; `go vet` checks the basic syntax.

**Memory layout.** Field order affects padding. This rarely matters except in hot, allocation-heavy structures.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Receivers and method sets | `go vet` (copylocks), compile-time `var _ I = (*T)(nil)` | Pick the receiver type and justify it |
| Construction | `NewX` functions, functional options | Design a small configurable type |
| Reflection on tags | `reflect.StructTag`, `json`, `go vet` structtag | Know what tags do and where they are read |
| Layout | `unsafe.Sizeof`, `fieldalignment` analyser | Understand padding, use only when profiling says so |

### Common mistakes

- Value receivers on a type that holds a mutex or needs mutation.
- Mixing value and pointer receivers on one type.
- Expecting embedded types to behave like virtual overrides.
- Returning a pointer to a local variable out of fear of "stack versus heap". Go handles that; the compiler decides (chapter 14).
- Unkeyed struct literals in code that will evolve.

### Self-check

- Why does a `T` not satisfy an interface whose method has a `*T` receiver?
- What is the difference between embedding a type and having a field of that type?
- Why is copying a struct that contains a `sync.Mutex` a bug?

## 6. Interfaces

**In plain words:** An interface is a list of methods. Any type that has those methods satisfies the interface automatically. You do not write "implements".

### Understand

**Implicit satisfaction.** A type implements an interface by having the right methods. There is no `implements` keyword. The consumer defines the interface it needs; the producer need not know. This inverts the Java and TypeScript habit of declaring interfaces next to implementations.

```go
type UserStore interface {
    Get(ctx context.Context, id int64) (User, error)
}

type Handler struct{ store UserStore } // depends on the behaviour it needs
```

A test can supply a tiny fake that satisfies `UserStore` with no mocking framework.

**Small interfaces.** The best Go interfaces have one or two methods (`io.Reader`, `io.Writer`, `fmt.Stringer`, `error`). Big interfaces make fakes expensive and couple consumers to producers. Compose small ones when needed.

**"Accept interfaces, return structs."** Functions should take the narrowest interface they need as parameters, and return concrete types so callers get the full API and the producer does not export an interface prematurely. Define interfaces where they are used, and only when there is a second implementation or a real testing need. Do not create an interface for every struct.

**What an interface value is.** An interface value is a pair: a dynamic type and a dynamic value. It is `nil` only when **both** are unset.

**The nil-interface trap.**

```go
type MyErr struct{}
func (*MyErr) Error() string { return "my error" }

func find() error {
    var e *MyErr // nil pointer
    return e     // interface holds (type *MyErr, value nil): NOT nil
}

func main() {
    if err := find(); err != nil {
        fmt.Println("non-nil error!") // this prints
    }
}
```

A nil `*MyErr` stored in an `error` makes a non-nil interface. The fix: return the literal `nil` on success paths, and never return a typed nil pointer as an interface. This is a well-known source of "error is non-nil but shows nothing" bugs in code that returns custom error types.

**Type assertions and switches.** `v, ok := x.(T)` asserts the dynamic type and does not panic when you use the two-value form. `switch v := x.(type)` branches on type. Use sparingly; frequent type switches suggest a missing method.

**`any`.** `any` is an alias for `interface{}`. It disables type checking. Prefer concrete types or generics (chapter 9). Values decoded from JSON into `any` become `map[string]any`, `[]any`, `float64`, `string`, `bool` or `nil`.

**Comparability.** Comparing two interface values with `==` panics at runtime if their dynamic types are identical and not comparable (for example both hold slices).

**Standard interfaces worth knowing.** `io.Reader`, `io.Writer`, `io.Closer`, `http.Handler`, `sort.Interface`, `json.Marshaler`, `sql.Scanner`, `driver.Valuer`, `context.Context`, `error`, `fmt.Stringer`. Composing readers and writers (`io.Copy`, `io.TeeReader`, `io.LimitReader`, `bufio`) is how Go streams data without loading it all into memory.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Satisfaction checks | `var _ I = (*T)(nil)`, compiler errors | Verify intent at compile time |
| Streaming | `io.Copy`, `io.Pipe`, `io.LimitReader`, `bufio.Scanner`, `bufio.Reader` | Process large bodies with bounded memory |
| Fakes in tests | hand-written fakes, embedding an interface in a struct | Test a handler without a mocking library |
| Generators | `mockgen`, `moq` | Know they exist, use when hand-written fakes are costly |

### Common mistakes

- Defining an interface next to its only implementation "just in case".
- Returning interfaces from constructors, hiding the concrete API.
- Returning a typed nil pointer as an interface value.
- Large interfaces with many methods.
- Using `any` where a small interface or generics would keep type safety.
- Reading an entire request or file into memory with `io.ReadAll` without a size limit.

### Self-check

- Why is `err != nil` true in the nil-pointer example, and how do you fix it?
- Where should an interface be declared: with the implementer or the consumer? Why?
- What does `io.Reader` allow that `[]byte` parameters do not?

## 7. Errors

**In plain words:** In Go, a function that can fail returns an error as a normal value. You check it right after the call. You add context when you pass it up, so the final message explains what went wrong.

### Understand

**Errors are values.** An `error` is an interface with `Error() string`. Functions return `(result, error)`, and the caller checks immediately. This makes failure paths visible in the code. Node's `try/catch` and rejected promises are replaced by explicit `if err != nil`.

```go
u, err := store.Get(ctx, id)
if err != nil {
    return User{}, fmt.Errorf("load user %d: %w", id, err)
}
```

**Add context, do not log and return.** Wrap with `fmt.Errorf("doing X: %w", err)` at each layer so the final message reads as a trace ("create order: charge card: dial tcp: timeout"). Handle an error once: either log it or return it, not both, or you get duplicate noise.

**Wrapping, `errors.Is`, `errors.As`.** `%w` wraps an error so it can be unwrapped. `errors.Is(err, target)` walks the chain looking for an equal value. `errors.As(err, &target)` walks the chain looking for a type and assigns it. Always use these instead of `==` or direct type assertions on errors that may be wrapped. `errors.Join` (Go 1.20) combines several errors. `%v` formats an error into text but breaks the chain; use `%w` when callers should be able to inspect the cause.

**Sentinel versus typed errors.**

```go
// Sentinel: compare identity with errors.Is
var ErrNotFound = errors.New("not found")

// Typed: carry data, find with errors.As
type ValidationError struct {
    Field string
    Msg   string
}
func (e *ValidationError) Error() string { return e.Field + ": " + e.Msg }

func handle(err error) {
    var ve *ValidationError
    switch {
    case errors.Is(err, ErrNotFound):
        // 404
    case errors.As(err, &ve):
        // 400, report ve.Field
    default:
        // 500
    }
}
```

Use a sentinel for a simple condition callers must branch on. Use a typed error when callers need structured data. Exported sentinels and types become part of your API, so keep them few. Map domain errors to HTTP status codes in one place at the boundary, not scattered through the code.

**Do not match on error strings.** Message text is not a contract.

**Wrapping drivers' errors.** For example `sql.ErrNoRows` should usually be translated at the repository boundary into your own `ErrNotFound`, so callers do not depend on the database package.

**Context errors.** `context.Canceled` and `context.DeadlineExceeded` are sentinels you test with `errors.Is`. A canceled request is often not worth an error-level log.

**Panics are not errors.** Use `panic` only for programmer errors and impossible states (chapter 8).

**Ignoring errors.** `_ = f()` is a deliberate statement; a bare `f()` that returns an error is a bug. Linters (`errcheck`, included in `golangci-lint`) catch it. Common deliberate cases are `defer resp.Body.Close()` and `defer f.Close()` on read-only files. For writes, `Close` can report a real failure, so check it.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Wrapping and inspection | `fmt.Errorf("%w")`, `errors.Is`, `errors.As`, `errors.Join`, `errors.Unwrap` | Build and read an error chain |
| Linting | `errcheck`, `errorlint` (via `golangci-lint`), `staticcheck` | Catch ignored errors and `==` comparisons |
| Boundary mapping | one function from error to HTTP status and body | Keep transport concerns out of domain code |
| Logging | `log/slog` (recent versions), structured fields | Log an error once, with context |

### Common mistakes

- Returning `err` without context, then debugging "EOF" with no origin.
- Using `%v` instead of `%w` and losing the ability to use `errors.Is`.
- Comparing wrapped errors with `==`.
- Logging and returning the same error at every layer.
- Returning a typed nil pointer as `error` (chapter 6).
- Exposing internal error text (SQL, file paths) to API clients.

## 8. defer, panic and recover

**In plain words:** `defer` runs a cleanup call when a function ends, such as closing a file. A panic [a crash of the current goroutine] is for serious programmer errors, not normal failures. `recover` can catch a panic, but only inside a deferred function.

### Understand

**defer** schedules a call to run when the surrounding function returns, in last-in first-out order. It is how Go pairs acquisition with release right next to each other.

```go
mu.Lock()
defer mu.Unlock()

f, err := os.Open(path)
if err != nil {
    return err
}
defer f.Close()
```

Rules that matter:

- **Arguments are evaluated when the `defer` statement executes**, not when the deferred call runs. The function body runs later.
- Deferred closures can read and modify **named result values**, which is how a function can convert a panic or add context to a returned error.
- A `defer` inside a loop runs at function exit, not at the end of each iteration. In a loop that opens many files, wrap the body in a function, or close explicitly.
- Deferred calls have a small cost and are fine in nearly all code.

```go
func work() (err error) {
    defer func() {
        if err != nil {
            err = fmt.Errorf("work: %w", err)
        }
    }()
    return step()
}
```

**panic** stops normal execution, runs deferred calls while unwinding, and, if nothing recovers, crashes the program with a stack trace. Runtime errors (nil dereference, index out of range, closing a closed channel, writing to a nil map) are panics.

**recover** returns the panic value when called directly from a deferred function, and stops the unwinding. Elsewhere it returns nil.

```go
func safe(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if v := recover(); v != nil {
                slog.Error("panic in handler", "value", v)
                http.Error(w, "internal error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}
```

**Where recover belongs.** At boundaries: a middleware around handlers, the top of a worker goroutine. The `net/http` server already recovers panics in handlers, logs and closes the connection, but custom middleware lets you return a clean 500 and emit metrics. A panic in a goroutine you started **cannot** be recovered by the parent. It crashes the whole process unless that goroutine recovers itself. This is the main difference from Node, where an unhandled rejection or exception policy is global.

**Do not use panic for control flow or expected failures.** Libraries should return errors. Panic is acceptable for programmer mistakes at startup (invalid regular expression via `regexp.MustCompile`, missing required configuration).

**`os.Exit` and `log.Fatal`** terminate immediately without running deferred calls. Use them only in `main`, ideally as `func main() { if err := run(); err != nil { ...; os.Exit(1) } }` so deferred cleanup in `run` executes.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Cleanup | `defer` with locks, files, bodies, transactions | Pair every acquire with a release |
| Panic boundaries | recover middleware, worker wrappers | Make no goroutine able to crash the process unseen |
| Reading crashes | stack traces, `GOTRACEBACK`, `runtime/debug.Stack` | Locate the origin of a panic from the trace |

### Common mistakes

- `defer` in a long loop, leaking files until function exit.
- Expecting `recover` to catch a panic in another goroutine.
- Calling `recover` outside a deferred function.
- Swallowing a panic with no log, hiding a real bug.
- Using `log.Fatal` deep in library code.

- Why can a deferred function change a function's return value?
- Why does a panic in a spawned goroutine take down the whole service?

## 9. Generics

**In plain words:** Generics let you write one function or type that works with many types. Use them for containers and small helpers. For most other cases, a plain interface is simpler.

### Understand

Generics (Go 1.18) let functions and types be parameterised by type, with constraints.

```go
type Number interface {
    ~int | ~int64 | ~float64
}

func Sum[T Number](xs []T) T {
    var total T
    for _, x := range xs {
        total += x
    }
    return total
}

type Cache[K comparable, V any] struct {
    mu sync.RWMutex
    m  map[K]V
}

func NewCache[K comparable, V any]() *Cache[K, V] {
    return &Cache[K, V]{m: make(map[K]V)}
}
```

Key points:

- `any` means no constraint. `comparable` means usable with `==` and as a map key.
- `~int` includes named types whose underlying type is `int`.
- Type arguments are usually inferred: `Sum(prices)`.
- Methods cannot have their own type parameters; only the type can.
- The standard library provides generic helpers in `slices`, `maps` and `cmp` (recent versions), and `sync/atomic` has generic `atomic.Pointer[T]`.

**When to use them.** Container types (caches, sets, queues), and utility functions over slices and maps that would otherwise be duplicated or use `any`. **When not to.** If an interface describes the behaviour you need, use the interface. Do not use generics to imitate inheritance or to avoid writing two lines twice. Go's guidance is to write concrete code first and generalise when duplication is real.

Generics are not a replacement for interfaces: interfaces give runtime polymorphism (different types behind one value); generics give compile-time reuse (one algorithm for many types).

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Constraints | `any`, `comparable`, `cmp.Ordered`, custom union interfaces | Write and read constraints |
| Standard helpers | `slices`, `maps`, `cmp` | Replace hand-written loops where clearer |
| Type-safe containers | generic cache, set, result pool | Build one small generic type |

### Common mistakes

- Reaching for generics instead of a plain interface.
- Over-constraining or under-constraining type parameters.
- Hiding a simple loop behind a clever generic helper.
- Expecting method-level type parameters.

### Self-check

- What do `any` and `comparable` permit?
- Give one case where an interface is better than a type parameter, and one for the reverse.

## 10. Goroutines and channels

**In plain words:** `go f()` starts a function in a new goroutine. A channel [a typed pipe between goroutines] lets goroutines send values safely. You must decide how each goroutine stops.

### Understand

**Starting a goroutine.** `go f(x)` runs `f` concurrently. The call returns immediately; arguments are evaluated at the `go` statement. The program exits when `main` returns, regardless of running goroutines. Nothing waits for goroutines unless you build the waiting.

**Goroutine lifetime is your responsibility.** For every goroutine you start, answer: who stops it, and how do I know it finished? Unanswered, this is a leak (chapter 13).

**Loop variable capture.** With Go 1.22 semantics (module `go` version 1.22 or newer), each iteration has its own variable, so this is correct:

```go
for _, id := range ids {
    go func() { process(id) }() // each iteration's own id
}
```

Under older semantics all goroutines could see the last value. Passing the variable as an argument (`go func(id int) { ... }(id)`) is correct in every version and self-documenting.

**Channels** are typed, thread-safe conduits for communication and synchronisation.

- **Unbuffered** `make(chan T)`: send and receive rendezvous. A send blocks until a receiver is ready. It synchronises two goroutines.
- **Buffered** `make(chan T, n)`: a send blocks only when the buffer is full; a receive blocks only when it is empty. A buffer provides decoupling and limited queueing, not unbounded storage. Do not size buffers to "fix" a deadlock.
- **Closing.** `close(ch)` signals that no more values will be sent. Only the **sender** closes, and only once. Rules:
  - Receiving from a closed channel returns remaining buffered values, then the zero value immediately with `ok == false`.
  - Sending on a closed channel panics. Closing a closed channel panics. Closing a nil channel panics.
  - Closing is optional and only needed to signal "done" to receivers, for example to end a `range`.
- **nil channel.** Send and receive on a nil channel block forever. This is useful in `select` to disable a case.
- **Direction types.** `chan<- T` is send-only, `<-chan T` is receive-only. Use them in signatures to document intent.
- `for v := range ch` receives until the channel is closed.
- `len(ch)` and `cap(ch)` exist but are racy for decisions.

**select** waits on several channel operations and proceeds with one that is ready. If several are ready, one is chosen pseudo-randomly. A `default` case makes it non-blocking.

```go
select {
case job := <-jobs:
    handle(job)
case <-ctx.Done():
    return ctx.Err()
case <-time.After(5 * time.Second):
    return errors.New("idle timeout")
}
```

Notes: `time.After` allocates a timer on each call. In a hot loop, use `time.NewTimer` with `Reset` and `Stop`. A `select` with only a blocked send can leak the goroutine if the receiver has gone, so always include a cancellation case on sends that may block.

**Done signals.** `chan struct{}` carries no data and signals events. Closing it broadcasts to all receivers, which is why `ctx.Done()` is a closed-on-cancel channel.

**Deadlocks.** If all goroutines are blocked, the runtime aborts with "all goroutines are asleep - deadlock!". This only detects the case where **every** goroutine is stuck. In a server with other running goroutines, a partial deadlock goes unnoticed and appears as hung requests.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Spawning safely | `sync.WaitGroup`, `errgroup`, `context` | Never start a goroutine without an exit path |
| Channel design | direction types, `chan struct{}`, `select` with `ctx.Done()` | Choose buffered vs unbuffered with a reason |
| Observing goroutines | `runtime.NumGoroutine()`, `/debug/pprof/goroutine?debug=2`, `GOTRACEBACK=all` | Dump all goroutines and read where they block |
| Testing leaks | `go.uber.org/goleak` | Fail tests that leak goroutines |

### Common mistakes

- Fire-and-forget goroutines with no cancellation.
- Closing a channel from the receiver side, or from multiple senders.
- Sending to a channel that nobody reads anymore.
- Using `time.Sleep` to wait for goroutines instead of `WaitGroup`.
- Unbounded goroutine creation per request or per item.
- Relying on `len(ch)` for logic.

## 11. The sync package, atomics and the memory model

**In plain words:** When goroutines share data, you must coordinate them. A mutex [a lock that lets one goroutine in at a time] protects shared data. Without coordination you get a data race, which causes wrong results that are hard to find.

### Understand

**Data race.** Two goroutines access the same memory concurrently, at least one writes, and there is no synchronisation ordering them. A data race is undefined behaviour in practice: torn values, lost updates, corrupted maps and slices. "It works on my machine" is not evidence of correctness.

**Mutex.** `sync.Mutex` gives exclusive access. Pair `Lock` with `defer Unlock`. Keep critical sections short and never do I/O or call unknown code while holding one. Locks are not reentrant: locking twice in one goroutine deadlocks. Never copy a mutex after first use.

```go
type Counter struct {
    mu sync.Mutex
    n  map[string]int
}

func (c *Counter) Inc(k string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.n[k]++
}
```

**RWMutex.** Allows many concurrent readers or one writer. It helps when reads dominate and the critical section is not tiny. It has more overhead than `Mutex`; measure before choosing it. A goroutine holding a read lock must not try to take the write lock.

**WaitGroup.** Waits for a set of goroutines. Call `Add` before starting the goroutine (not inside it), `Done` when each finishes, `Wait` to block. Go 1.25 adds `wg.Go(func())`, which does the `Add`, the `go` statement and the `Done` for you.

```go
var wg sync.WaitGroup
for _, u := range urls {
    wg.Add(1)
    go func() {
        defer wg.Done()
        fetch(u)
    }()
}
wg.Wait()
```

**Once.** `sync.Once.Do(f)` runs `f` exactly once, with later callers waiting for completion. Use for lazy initialisation. `sync.OnceFunc` and `OnceValue` (Go 1.21) wrap this.

**sync.Pool.** A cache of temporary objects to reduce allocation (buffers). Items may be dropped at any GC. Not for connection pooling or anything that must persist.

**sync.Map.** A concurrent map optimised for narrow patterns. In most code a plain map with a mutex is clearer and faster.

**sync.Cond.** Condition variables. Rarely needed; channels usually express it better.

**Atomics.** `sync/atomic` provides lock-free operations on single values. The typed API (`atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`, Go 1.19) is preferred over the function forms.

```go
var requests atomic.Int64
requests.Add(1)
n := requests.Load()
```

Use atomics for counters, flags and swapping an immutable config pointer. Use a mutex when several fields must change together. An atomic on one field does not protect invariants across fields.

**Memory model (basics).** The Go memory model defines when a write by one goroutine is guaranteed visible to a read in another: through **happens-before** relationships created by synchronisation. Practical rules:

- A send on a channel happens before the corresponding receive completes. Closing a channel happens before a receive that observes the close.
- For an unbuffered channel, a receive happens before the corresponding send completes.
- `Unlock` happens before a later `Lock` of the same mutex.
- `wg.Done` happens before `wg.Wait` returns. `once.Do(f)` return happens after `f` completes.
- The `go` statement happens before the goroutine starts.
- A goroutine's exit is **not** synchronised with anything unless you use one of the above.

If your code is race-free using these tools, you get sequentially consistent behaviour for those accesses. Do not write "benign" races, such as an unsynchronised boolean flag read in a loop. The compiler may hoist the read and the loop may never end.

**Channels or mutexes?** Use channels to transfer ownership of data, coordinate stages and signal events. Use mutexes to protect shared state such as caches, counters and registries. A mutex-guarded struct with methods is often the simplest correct answer.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Detecting races | `go test -race`, `go run -race`, `go build -race` | Run in CI, read a race report |
| Locks | `sync.Mutex`, `sync.RWMutex`, `defer Unlock`, `go vet` copylocks | Guard state with small critical sections |
| Coordination | `sync.WaitGroup`, `sync.Once`, `errgroup` | Wait for completion and run initialisation once |
| Lock-free | `sync/atomic` typed values | Implement a safe counter or config swap |
| Contention | `pprof` mutex and block profiles | Find a hot lock |

### Common mistakes

- `wg.Add(1)` inside the goroutine, racing with `Wait`.
- Copying a struct that contains a `Mutex` or `WaitGroup`.
- Holding a lock while doing network I/O.
- Reading a map under `RLock` while another path writes without a lock.
- Inconsistent lock acquisition order across code paths, causing deadlock.
- Using an unsynchronised flag for shutdown.

## 12. context

**In plain words:** A context is a value you pass through your calls. It tells all the work for one request to stop when the client leaves or time runs out. Every blocking call should receive it.

### Understand

`context.Context` carries **cancellation, deadlines and request-scoped values** across API boundaries and goroutines. It is the mechanism that stops work nobody is waiting for any more. A client disconnects, a deadline passes, or a sibling task fails: the context is cancelled, and everything using it should stop.

**Basics.**

- `context.Background()` is the root for `main`, tests and top-level jobs. In an HTTP handler use `r.Context()`, which is cancelled when the client goes away or the request ends.
- `context.WithCancel(parent)` returns a derived context and a `cancel` function.
- `context.WithTimeout(parent, d)` and `WithDeadline(parent, t)` cancel automatically.
- Cancelling a parent cancels all children, never the reverse.
- **Always call `cancel`** (usually `defer cancel()`) to release timers and resources, even if the context times out on its own. `go vet` warns about a discarded cancel function.
- `ctx.Done()` is a channel closed on cancellation. `ctx.Err()` returns `context.Canceled` or `context.DeadlineExceeded`.
- `context.WithCancelCause` and `context.Cause` (Go 1.20) record why a context was cancelled.

**Conventions (from the standard library docs).**

- Pass `ctx` as the **first parameter**, named `ctx`.
- Do not store a context in a struct field for later use; pass it per call. (Short-lived request objects are the exception.)
- Do not pass a nil context. Use `context.TODO()` as a placeholder when unsure.
- Use `context.WithValue` only for request-scoped data that crosses APIs (request ID, authenticated principal), with an unexported key type, never for optional function parameters.

```go
type ctxKey struct{}

func WithRequestID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, ctxKey{}, id)
}

func RequestID(ctx context.Context) string {
    id, _ := ctx.Value(ctxKey{}).(string)
    return id
}
```

**Using it for real.** The context must reach every blocking operation: `db.QueryContext(ctx, ...)`, `http.NewRequestWithContext(ctx, ...)`, `select` on `ctx.Done()`, loops doing long CPU work that check `ctx.Err()` periodically. Libraries that accept a context but are never passed a real one give you no cancellation.

```go
ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
defer cancel()

req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
if err != nil {
    return err
}
resp, err := client.Do(req)
```

**Timeout budgets.** A deadline set at the edge propagates inward. Each downstream call should have a timeout no larger than the time left. Derive child contexts with shorter timeouts when a dependency needs its own bound. Cancelling is cooperative: a function that ignores the context keeps running. This is the Go equivalent of `AbortController` and `AbortSignal` in Node, but pervasive and part of every function signature.

**Detached work.** When you must finish something after the request ends (an audit write), do not reuse the cancelled request context. Create a new context with its own timeout (`context.WithoutCancel`, Go 1.21, keeps values but drops cancellation). Be deliberate, since it leaves the request's lifetime.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Creation | `WithCancel`, `WithTimeout`, `WithDeadline`, `WithCancelCause`, `WithoutCancel` | Pick the right constructor and always cancel |
| Propagation | `r.Context()`, `QueryContext`, `NewRequestWithContext`, `signal.NotifyContext` | Thread ctx through every blocking call |
| Checking | `ctx.Done()`, `ctx.Err()`, `errors.Is(err, context.DeadlineExceeded)` | Handle cancellation in loops and selects |
| Static checks | `go vet` lostcancel | Catch a dropped cancel function |

### Common mistakes

- Dropping `cancel`, leaking timers.
- Starting a goroutine in a handler that uses `r.Context()` after the handler returns.
- Passing `context.Background()` deep in code, breaking cancellation.
- Using `WithValue` as a way to pass dependencies or optional parameters.
- Treating `DeadlineExceeded` from a downstream call as an internal error rather than a timeout class of its own.

## 13. Concurrency patterns and leaks

**In plain words:** Do not start unlimited goroutines. Use a fixed number of workers, and give each goroutine a way to stop. A goroutine leak [a goroutine that never ends] slowly uses all your memory.

### Understand

**Bounded concurrency is the default design rule.** Unlimited goroutines per request or per item exhaust memory, connections or downstream capacity. Every pattern below exists to bound and coordinate work.

**Worker pool.** A fixed number of workers read jobs from a channel.

```go
func process(ctx context.Context, jobs <-chan Job, workers int) error {
    g, ctx := errgroup.WithContext(ctx)
    for i := 0; i < workers; i++ {
        g.Go(func() error {
            for {
                select {
                case <-ctx.Done():
                    return ctx.Err()
                case j, ok := <-jobs:
                    if !ok {
                        return nil
                    }
                    if err := handle(ctx, j); err != nil {
                        return err
                    }
                }
            }
        })
    }
    return g.Wait()
}
```

The producer closes `jobs` when finished. Workers exit on a closed channel or a cancelled context.

**errgroup** (`golang.org/x/sync/errgroup`). Runs goroutines, waits for all, returns the first non-nil error, and (with `WithContext`) cancels the derived context on first failure. `g.SetLimit(n)` bounds concurrency, making `g.Go` block until a slot is free. It replaces most hand-rolled `WaitGroup` plus error channel code. It is in the `x` repository, so add it as a dependency and confirm the API in its docs.

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8)
for _, id := range ids {
    g.Go(func() error { return fetchOne(ctx, id) })
}
if err := g.Wait(); err != nil {
    return err
}
```

(This uses Go 1.22 loop-variable semantics; otherwise copy `id` first.)

**Fan-out and fan-in.** Fan-out: several goroutines read from one channel to parallelise work. Fan-in: merge several result channels into one. A fan-in needs a `WaitGroup` that closes the merged channel after all inputs finish.

**Pipeline.** Stages connected by channels: each stage receives from upstream, does work, sends downstream, and closes its output when its input closes. Every stage takes a context and selects on `ctx.Done()` when sending, so an early exit downstream does not strand upstream goroutines.

```go
func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for v := range in {
            select {
            case out <- v * v:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}
```

**Other useful patterns.**

- **Semaphore:** a buffered channel of `struct{}` or `golang.org/x/sync/semaphore` to limit concurrent calls.
- **Rate limiting:** `golang.org/x/time/rate` token bucket.
- **Single flight:** `golang.org/x/sync/singleflight` collapses duplicate concurrent calls (cache stampede protection).
- **Timeouts and retries:** exponential backoff with jitter, bounded attempts, respect the context, retry only idempotent operations.

**Goroutine leaks.** A leak is a goroutine that can never finish, usually blocked forever on a channel, lock, or I/O. Each leaked goroutine retains its stack and everything it references. Typical causes:

- Sending to a channel whose receiver returned early (for example after a timeout).
- Receiving from a channel nobody closes.
- No cancellation path for a background loop (a ticker goroutine with no stop).
- A request-scoped goroutine blocked on a call with no timeout.
- A forgotten `time.Ticker` (call `Stop`).

A classic leak: a timeout returns early, but the worker goroutine later blocks sending its result on an unbuffered channel nobody reads. Fix with a buffered channel of size 1 so the send always completes, or a `select` with `ctx.Done()`.

**Detecting leaks.** Watch `runtime.NumGoroutine()` or a goroutine-count metric trending upward. Fetch `/debug/pprof/goroutine?debug=2` and group identical stacks. Use `goleak` in tests.

**Shutdown ordering.** Stop accepting work, cancel contexts, wait for in-flight work with a deadline, then close resources (database, queues) in reverse order of creation.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Group management | `errgroup`, `SetLimit`, `WithContext` | Run N tasks with bounded concurrency and first-error cancellation |
| Limiting | buffered-channel semaphore, `x/sync/semaphore`, `x/time/rate` | Bound concurrency and rate |
| Deduplication | `x/sync/singleflight` | Prevent stampedes on a cache miss |
| Leak finding | `pprof` goroutine profile, `goleak`, `runtime.NumGoroutine` | Identify the blocking line from a dump |
| Retries | backoff with jitter, `context` aware sleeps | Retry safely without amplifying outages |

### Common mistakes

- Spawning one goroutine per item for unbounded input.
- Closing the results channel before all workers finish.
- Unbuffered result channel plus an early-return path.
- Ignoring errors from goroutines, because there is nowhere to return them. Collect them with `errgroup`.
- Retrying non-idempotent operations or retrying without a limit.
- Shutting down by cancelling and exiting without waiting for workers.

## 14. Memory: escape analysis and the garbage collector

**In plain words:** Go frees memory for you with a garbage collector [a runtime part that finds and frees unused memory]. The compiler decides if a value lives on the stack [fast, per-call memory] or the heap [shared memory the collector manages]. Fewer allocations mean less collector work.

### Understand

**Stack versus heap.** Each goroutine has its own stack, cheap to allocate and free with the function call. The heap is managed by the garbage collector. You do not choose; the compiler's **escape analysis** decides. A value stays on the stack if the compiler can prove it does not outlive the function. It escapes to the heap in several cases. Examples: its address is returned, it is stored where the compiler cannot track it, a closure that outlives the call captures it, or its size is not known at compile time. Returning a pointer to a local variable is safe and common; the variable simply escapes.

```
go build -gcflags=-m ./...   # prints escape and inlining decisions
```

Treat that output as a diagnostic, not a goal. Avoid micro-optimising escapes until a profile points at allocation.

**Why allocation matters.** Each heap allocation costs allocator time and adds GC work. In hot paths, allocation rate dominates latency tails. Typical sources: `fmt.Sprintf`, string concatenation, converting between `string` and `[]byte`, boxing values into interfaces, growing slices, closures, per-request buffers. Remedies: preallocate with `make`, reuse buffers (`sync.Pool`, `bytes.Buffer.Reset`), use `strings.Builder`, avoid unnecessary pointers.

**Garbage collector (conceptual).** Go uses a concurrent, non-generational, tri-colour mark-and-sweep collector. Most marking runs concurrently with your code using spare CPU, with short stop-the-world pauses. It does not compact the heap. Consequences:

- GC cost is proportional to the **live heap** (what must be scanned), not garbage. Many small pointer-rich objects cost more to scan than large pointer-free ones (such as `[]byte`).
- Throughput trade-off: more live heap and more allocations mean more GC CPU, shown as CPU stolen from request handling.
- Tuning knobs: `GOGC` (default 100) sets how much the heap may grow relative to live data before the next cycle; a higher value uses more memory and less CPU. `GOMEMLIMIT` (Go 1.19) sets a soft memory limit so the collector works harder as usage nears it. In containers, set `GOMEMLIMIT` somewhat below the container limit to avoid OOM kills (chapter 6 of `03_Linux.md`), and confirm exact semantics in the GC guide.
- Go does not return memory to the OS instantly. RSS can stay above live heap. Compare `HeapInuse`, `HeapIdle` and RSS before diagnosing a "leak".

**Real leaks in Go** are almost always references you keep: an ever-growing map or cache with no eviction, goroutines holding references, sub-slices pinning large arrays, un-stopped tickers, global registries, appended-to slices that are never trimmed.

**Observing.** `runtime.ReadMemStats` or `runtime/metrics`, `GODEBUG=gctrace=1` for per-cycle logs, heap and allocs profiles from pprof (chapter 20).

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Escape analysis | `go build -gcflags=-m`, `-m=2` | Read why a value escaped |
| Allocation measurement | `go test -bench . -benchmem`, pprof `allocs` profile | Count allocations per operation and reduce them |
| GC behaviour | `GODEBUG=gctrace=1`, `runtime/metrics`, `GOGC`, `GOMEMLIMIT` | Explain a GC log line and pick a limit for a container |
| Heap inspection | pprof `heap` profile (`inuse_space`, `alloc_space`) | Find what holds memory |

### Common mistakes

- Optimising allocations without a benchmark or profile.
- Unbounded in-memory caches and maps.
- Calling `runtime.GC()` in production code to "fix" memory.
- Setting no `GOMEMLIMIT` in a memory-limited container and being OOM-killed.
- Confusing a high RSS with a leak, or ignoring a steadily rising live heap.

## 15. net/http: server and client

**In plain words:** The standard library can run a web server and call other servers. The default settings have no timeouts, so you must set them. You must also stop the server carefully, so running requests can finish.

### Understand

**Handlers.** `http.Handler` is the interface `ServeHTTP(http.ResponseWriter, *http.Request)`. `http.HandlerFunc` adapts a function. **Middleware** is a function that takes a handler and returns a handler (logging, recover, auth, request ID, timeouts). `http.ServeMux` routes; Go 1.22 and later support methods and path wildcards in patterns such as `"GET /users/{id}"` with `r.PathValue("id")`. Many teams use `chi` or other routers on top of the standard types.

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
})
```

Handlers run concurrently, one goroutine per request. Any shared state they touch needs synchronisation. Write headers before the body; after the first `Write`, status and headers are fixed. Set `Content-Type` explicitly. Limit request bodies with `http.MaxBytesReader`.

**Server timeouts: set them.** The zero-value `http.Server` has no timeouts. A slow client can hold a connection and goroutine open forever (Slowloris). `http.ListenAndServe` uses that zero-value server, so it is not production-ready.

| Field | Protects against |
|---|---|
| `ReadHeaderTimeout` | clients that send headers slowly |
| `ReadTimeout` | slow request bodies (covers headers and body) |
| `WriteTimeout` | slow readers of the response; also bounds handler time for the write |
| `IdleTimeout` | idle keep-alive connections |
| `MaxHeaderBytes` | oversized headers |

Per-request limits inside handlers use `context.WithTimeout` or `http.TimeoutHandler`. Streaming endpoints (SSE, large downloads) conflict with a short `WriteTimeout`; use `http.ResponseController` (Go 1.20 and later) to adjust the deadline per request, for example with `SetWriteDeadline`.

**Graceful shutdown.** On `SIGTERM` (chapter 4 of `03_Linux.md`), stop accepting new connections, finish in-flight requests, then exit. `Server.Shutdown(ctx)` does this; it waits for active requests until `ctx` expires. `ListenAndServe` returns `http.ErrServerClosed` immediately after `Shutdown` is called, which is not a failure.

```go
func run() error {
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    srv := &http.Server{
        Addr:              ":8080",
        Handler:           newRouter(),
        ReadHeaderTimeout: 5 * time.Second,
        ReadTimeout:       15 * time.Second,
        WriteTimeout:      30 * time.Second,
        IdleTimeout:       60 * time.Second,
    }

    errCh := make(chan error, 1)
    go func() { errCh <- srv.ListenAndServe() }()

    select {
    case err := <-errCh:
        return err // failed to start
    case <-ctx.Done():
    }

    shutdownCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
    defer cancel()
    return srv.Shutdown(shutdownCtx)
}
```

Choose the shutdown timeout to be less than the orchestrator's kill grace period (for example Kubernetes `terminationGracePeriodSeconds`, or `TimeoutStopSec` in systemd). A readiness endpoint should start failing when shutdown begins so the load balancer drains traffic. `Shutdown` does not wait for hijacked connections (WebSockets); register cleanup with `RegisterOnShutdown` and confirm details in the docs.

**Client.** `http.Client` is safe for concurrent use and should be **reused**; it owns a `Transport` with a connection pool.

- The zero `http.Client` and `http.DefaultClient` have **no timeout**. Always set `Client.Timeout` (a whole-exchange bound) and/or use `context` per request.
- Tune `Transport`: `MaxIdleConnsPerHost` (default is small, 2), `IdleConnTimeout`, `TLSHandshakeTimeout`, dial timeouts via `net.Dialer`. Many parallel calls to one host with the default idle limit cause constant reconnects.
- **Always close `resp.Body`**, and to reuse the connection, read it to EOF (or discard the remainder) before closing. Not closing leaks connections and goroutines.
- A non-2xx status is **not** an error from `client.Do`; check `resp.StatusCode`.
- Use `http.NewRequestWithContext`.

```go
client := &http.Client{Timeout: 10 * time.Second}

resp, err := client.Do(req)
if err != nil {
    return err
}
defer resp.Body.Close()
if resp.StatusCode != http.StatusOK {
    io.Copy(io.Discard, io.LimitReader(resp.Body, 1<<20))
    return fmt.Errorf("unexpected status %d", resp.StatusCode)
}
```

**Practical service concerns.** Health and readiness endpoints, request IDs, structured logs, metrics (Prometheus client library is common), TLS usually terminated at a proxy or load balancer, trusting `X-Forwarded-*` headers only from known proxies (chapter 7 of `03_Linux.md`), and `net/http/pprof` exposed only on an internal port.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Serving | `http.Server`, `ServeMux`, middleware chains, `http.MaxBytesReader` | Build a service with all four timeouts set |
| Shutdown | `signal.NotifyContext`, `Server.Shutdown`, `RegisterOnShutdown` | Drain in-flight requests within a bounded time |
| Client | `http.Client`, `http.Transport`, `NewRequestWithContext` | Reuse a client with sane timeouts and pooling |
| Testing | `net/http/httptest` (`NewRecorder`, `NewServer`) | Test handlers and clients without a network |
| Manual checks | `curl -v`, `curl -w`, `hey`, `wrk`, `vegeta` | Exercise timeouts and measure latency |

### Common mistakes

- `http.ListenAndServe` or a server with no timeouts in production.
- Using `http.DefaultClient`, or creating a new client per request, defeating pooling.
- Forgetting to close or drain `resp.Body`.
- Doing work in a handler after the client has gone, ignoring `r.Context()`.
- Writing the status code after the body, or calling `WriteHeader` twice.
- Exiting on `SIGTERM` without draining, dropping in-flight requests during deploys.
- Exposing `/debug/pprof` on the public listener.

## 16. encoding/json

**In plain words:** This package converts Go values to JSON text and back. It uses struct tags [short labels on fields that set the JSON name]. Only fields that start with a capital letter are converted.

### Understand

**Marshalling.** `json.Marshal(v)` produces JSON from a value; `json.Unmarshal(data, &v)` parses into a pointer. For streams (HTTP bodies, files) use `json.NewDecoder(r)` and `json.NewEncoder(w)`, which avoid buffering a whole payload.

```go
type CreateOrder struct {
    CustomerID int64    `json:"customer_id"`
    Items      []string `json:"items"`
    Note       *string  `json:"note,omitempty"`
}

func decode(w http.ResponseWriter, r *http.Request) (CreateOrder, error) {
    var in CreateOrder
    dec := json.NewDecoder(http.MaxBytesReader(w, r.Body, 1<<20))
    dec.DisallowUnknownFields()
    if err := dec.Decode(&in); err != nil {
        return in, fmt.Errorf("decode body: %w", err)
    }
    return in, nil
}
```

(Pass the handler's `w` to `MaxBytesReader`, so the server can close the connection when the limit is reached.)

**Rules and behaviour to know.**

- Only **exported** fields are encoded or decoded. A lower-case field is silently ignored, a classic "why is my field empty" bug.
- Tags: `json:"name"`, `json:"name,omitempty"`, `json:"-"`, and `,string` for quoted numbers. `omitempty` omits zero values (empty string, 0, false, nil pointer, empty slice or map); it does not omit a zero struct. Go 1.24 adds `omitzero`, which omits any field whose value is zero, including a zero struct and a zero `time.Time`.
- **Zero versus absent.** Decoding into a plain `int` cannot distinguish a missing field from `0`. Use a pointer (`*int`) or a custom type when the difference matters (PATCH semantics).
- **Unknown fields** are ignored by default. `DisallowUnknownFields` makes the decoder strict.
- **Numbers into `any`** decode as `float64`, which loses precision for large integers (above 2^53). Use typed structs, `json.Number` via `dec.UseNumber()`, or strings for big IDs.
- **nil versus empty slices:** nil encodes as `null`, empty as `[]`. Clients often expect `[]`, so initialise.
- **`time.Time`** marshals as RFC 3339. `time.Duration` marshals as an integer of nanoseconds, which is rarely what an API wants; define a custom type.
- **`[]byte`** encodes as base64.
- **Maps** encode with keys sorted, so output is deterministic. Map decoding yields unordered Go maps.
- **Custom behaviour:** implement `MarshalJSON` and `UnmarshalJSON` (or the `encoding.TextMarshaler` interfaces). `json.RawMessage` defers decoding of a part, useful for envelope-with-type-field payloads.
- Trailing data after the first JSON value is not an error with `Decoder.Decode` unless you check for it.
- Errors: `*json.SyntaxError`, `*json.UnmarshalTypeError`, `io.EOF` for an empty body, which you should map to a 400 response.
- **Performance:** reflection-based encoding is adequate for most services. Faster third-party encoders exist; profile before adopting one. Go 1.25 includes an experimental `encoding/json/v2`, enabled only with `GOEXPERIMENT=jsonv2` at build time. Do not rely on it in production code.

**Security and API hygiene.** Limit body size, validate after decoding (decoding succeeds on well-typed garbage), and use separate request and response structs from your database and domain models, so internal fields are not exposed accidentally.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Streaming | `json.NewDecoder`, `json.NewEncoder`, `http.MaxBytesReader` | Parse bodies with bounded memory and strictness |
| Customisation | struct tags, `MarshalJSON`, `UnmarshalJSON`, `json.RawMessage`, `json.Number` | Handle absent versus zero and large numbers |
| Inspection | `jq`, `json.Indent`, `json.Valid` | Compare real payloads with the struct |
| Validation | hand-written checks, a validator library | Reject bad input after decoding |

### Common mistakes

- Unexported field names, so nothing is encoded.
- Decoding PATCH bodies into plain value fields and overwriting data with zeros.
- Decoding large IDs into `any` and losing precision.
- Returning `null` where clients expect an empty array.
- Exposing database models directly as API responses.
- No body size limit.

## 17. database/sql and connection pooling

**In plain words:** `sql.DB` is not one connection. It is a pool [a set of open connections that are reused]. Create it once, set limits, and always close rows and finish transactions.

### Understand

`database/sql` is a generic interface over relational databases with a built-in **connection pool**; a driver registers itself via a blank import (for PostgreSQL commonly `pgx` via its `stdlib` adapter or `lib/pq`; for MySQL `go-sql-driver/mysql`). Higher-level options exist: `sqlx` (convenience over `database/sql`), `pgx` native API, `sqlc` (generates type-safe Go from SQL), and ORMs such as GORM. Many teams favour plain SQL with `sqlc` or `sqlx`. Choose and document one.

**`*sql.DB` is a pool, not a connection.** Create it once at startup, share it everywhere, and close it at shutdown. `sql.Open` only validates arguments and does not connect; call `db.PingContext(ctx)` to verify connectivity.

```go
db, err := sql.Open("pgx", dsn)
if err != nil {
    return err
}
db.SetMaxOpenConns(20)
db.SetMaxIdleConns(10)
db.SetConnMaxLifetime(30 * time.Minute)
db.SetConnMaxIdleTime(5 * time.Minute)
if err := db.PingContext(ctx); err != nil {
    return err
}
```

**Pool settings.**

- `SetMaxOpenConns(n)`: cap on simultaneous connections. The default is unlimited, which under load can exceed the database's connection limit. Size so that (instances × max open) stays under the server's limit, leaving room for admin and migrations.
- `SetMaxIdleConns(n)`: connections kept ready. Default is small (2). Too low causes reconnect churn; keep it near the open cap for steady traffic.
- `SetConnMaxLifetime`: recycles connections, helping with load balancers, failovers and DNS changes.
- `SetConnMaxIdleTime`: closes long-idle connections.
- When all connections are in use, further calls **block** until one frees up or the context ends. This is how pool exhaustion appears: latency climbs while the database itself looks idle. Always pass a context with a deadline.
- `db.Stats()` reports `InUse`, `Idle`, `WaitCount` and `WaitDuration`. Export them as metrics.

**Queries.**

- `QueryContext` returns `*sql.Rows`: **always** `defer rows.Close()`, iterate with `rows.Next()`, call `rows.Scan`, and check `rows.Err()` after the loop. Forgetting `Close` leaks a connection from the pool.
- `QueryRowContext(...).Scan(...)` for one row; it returns `sql.ErrNoRows` when none. Translate that into your own not-found error.
- `ExecContext` for writes; it returns `sql.Result` (rows affected, last insert ID depending on driver).
- Use **placeholders** (`$1` for PostgreSQL, `?` for MySQL), never string concatenation, to prevent SQL injection and allow plan reuse.
- NULL handling: scan into `sql.NullString`, `sql.NullInt64` and friends, or pointers, or use `COALESCE`.
- Prepared statements (`db.PrepareContext`) are tied to connections; most code relies on driver-level handling, so confirm your driver's behaviour.

```go
func (r *Repo) Get(ctx context.Context, id int64) (User, error) {
    var u User
    err := r.db.QueryRowContext(ctx,
        `SELECT id, name FROM users WHERE id = $1`, id,
    ).Scan(&u.ID, &u.Name)
    if errors.Is(err, sql.ErrNoRows) {
        return User{}, ErrNotFound
    }
    return u, err
}
```

**Transactions.** `tx, err := db.BeginTx(ctx, nil)` pins one connection until `Commit` or `Rollback`. The idiom is `defer tx.Rollback()` right after `Begin` (rollback after a successful commit is a harmless no-op returning `sql.ErrTxDone`), then `tx.Commit()` at the end. Use the `tx` for every statement inside the transaction. Mixing `db` and `tx` calls runs the former outside the transaction and can deadlock when the pool is small. Keep transactions short. Do not make network calls in them.

**Context cancellation.** Passing a context lets the driver cancel a running query when the request is cancelled; whether the server-side query stops depends on the driver and database, so also configure server-side statement timeouts.

**Migrations.** Use a migration tool (`golang-migrate`, `goose`, `atlas`) with versioned SQL files, run as a separate deploy step rather than implicitly by every instance.

**Repository boundary.** Keep SQL in a repository or store package behind a small consumer-defined interface. Map driver errors to domain errors there.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Pool tuning | `SetMaxOpenConns`, `SetMaxIdleConns`, `SetConnMaxLifetime`, `db.Stats()` | Size a pool against the database limit and explain exhaustion |
| Query patterns | `QueryContext`, `QueryRowContext`, `ExecContext`, `sql.Null*` | Write leak-free queries with correct NULL handling |
| Transactions | `BeginTx`, `defer Rollback`, isolation levels | Implement an atomic multi-statement operation |
| Query generation | `sqlc`, `sqlx`, `pgx` | Pick one and justify it |
| Migrations | `golang-migrate`, `goose`, `atlas` | Run versioned, reversible migrations |
| Diagnosis | `EXPLAIN ANALYZE`, `pg_stat_activity`, pool metrics | Tell a slow query from pool starvation |

### Common mistakes

- Opening a `*sql.DB` per request.
- Not closing `rows`, slowly exhausting the pool.
- Skipping `rows.Err()`.
- Leaving `MaxOpenConns` unlimited and hitting `too many connections`.
- Using `db` inside a transaction instead of `tx`.
- Building SQL by string formatting.
- Holding a transaction open across an HTTP call.

## 18. Project layout

**In plain words:** Go does not force a folder structure. Keep the code in small packages named by what they do. Put the start-up wiring in `main`, and the rest in `internal/`.

### Understand

Go does not mandate a layout. The language rules that shape one: a directory is a package, packages cannot import cyclically, and `internal/` directories are importable only from within the parent tree. Start simple and add structure when needed.

**A common service layout.**

```
orders/
  go.mod
  cmd/
    api/main.go          # wiring only: config, dependencies, start server
    worker/main.go
  internal/
    order/               # domain types and logic
    httpapi/             # handlers, routing, middleware
    postgres/            # repository implementations
    config/
  migrations/
  Makefile
```

- **`cmd/<name>/main.go`**: one directory per binary. Keep `main` thin: parse config, construct dependencies, call `run()`.
- **`internal/`**: code that must not be imported by other modules. Put most application code here, so you can change it freely.
- **`pkg/`**: a convention for public library code; optional and debated. Prefer exposing nothing until needed.
- Organise by **domain or capability**, not by technical layer names like `models`, `controllers`, `utils`, which breed cycles and vague packages.
- **Package naming:** short, lower-case, singular, no underscores. The package name is part of the call site (`order.New`, not `order.NewOrder` in package `order`; avoid stutter). Avoid `util`, `common`, `helpers`.
- **Dependency injection** is by constructor parameters and consumer-defined interfaces, wired explicitly in `main`. A DI framework is rarely needed.
- **Configuration** from environment variables, parsed once into a struct and validated at startup; fail fast.
- **Logging** with `log/slog` (recent versions) or a structured logger, passed in or derived from context. Avoid global mutable state.
- **A `Makefile` or task runner** for build, test, lint, and run. Containerise with a multi-stage Dockerfile building a static binary into a minimal image.
- The "standard Go project layout" repository on GitHub is a community convention, not an official standard; the official guidance is the Go documentation on organising a module.

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Module structure | `cmd/`, `internal/`, `go list ./...` | Lay out a multi-binary service |
| Boundaries | consumer-defined interfaces, constructors | Wire dependencies in `main` only |
| Architecture checks | `go list -deps`, import-cycle errors, `depguard` (via lint) | Enforce layering mechanically |
| Packaging | multi-stage Dockerfile, `-trimpath`, `CGO_ENABLED=0` | Ship a small static image |

### Common mistakes

- Layer-named packages that import each other.
- Package names like `utils` that grow without cohesion.
- Business logic in `main` or in HTTP handlers, making it hard to test.
- Global variables for database handles and configuration.
- Premature abstractions: a `repository` interface and mocks for every table before there is a need.

### Self-check

- What does `internal/` enforce?
- Why organise packages by domain rather than by technical layer?
- Where does dependency wiring belong, and why?

## 19. Testing

**In plain words:** Go has testing built in, so you need no extra framework. A table-driven test [one test function that runs a list of cases] is the usual style. You can also run benchmarks and fuzz tests [tests with generated random input].

### Understand

Testing is part of the toolchain. Files named `*_test.go` and functions `func TestXxx(t *testing.T)` run with `go test`. No external framework is required.

**Table-driven tests.** The idiomatic style: a slice of cases, run each as a subtest.

```go
func TestParseSize(t *testing.T) {
    tests := []struct {
        name    string
        in      string
        want    int64
        wantErr bool
    }{
        {"bytes", "10", 10, false},
        {"kilo", "2K", 2048, false},
        {"empty", "", 0, true},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := ParseSize(tt.in)
            if (err != nil) != tt.wantErr {
                t.Fatalf("err = %v, wantErr %v", err, tt.wantErr)
            }
            if got != tt.want {
                t.Errorf("got %d, want %d", got, tt.want)
            }
        })
    }
}
```

With `t.Parallel()` inside subtests, loop-variable semantics matter: under Go 1.22 semantics `tt` is per-iteration; under older semantics you needed `tt := tt`. Use `t.Fatalf` when continuing makes no sense and `t.Errorf` to report and continue. Include inputs in failure messages. `t.Helper()` marks helper functions so failures point at the caller. `t.Cleanup` registers teardown. `t.TempDir()` gives a per-test directory. `t.Setenv` sets an environment variable for the test.

**Assertions.** The standard library has none; compare and call `t.Errorf`. `github.com/google/go-cmp/cmp` gives readable diffs (`cmp.Diff`). `testify` is popular; the choice is a team convention.

**Testing HTTP.** `net/http/httptest` has `NewRecorder` to call a handler directly and `NewServer` to start a real local server for client tests.

```go
func TestHealth(t *testing.T) {
    rec := httptest.NewRecorder()
    req := httptest.NewRequest(http.MethodGet, "/healthz", nil)
    newRouter().ServeHTTP(rec, req)
    if rec.Code != http.StatusOK {
        t.Fatalf("status = %d", rec.Code)
    }
}
```

**Fakes over mocks.** Because interfaces are implicit and small, a hand-written in-memory fake of `UserStore` is usually clearer than a generated mock. For database code, prefer tests against a real database (a container, for example with `testcontainers-go`, or a dedicated test schema) to verify SQL and migrations, since a mocked driver does not test your queries.

**Benchmarks.** `func BenchmarkXxx(b *testing.B)`; run with `go test -bench . -benchmem`. Loop `for i := 0; i < b.N; i++`. Go 1.24 adds the simpler `for b.Loop() { ... }`. Report allocations. Compare before and after with `benchstat` (from `golang.org/x/perf`), running multiple iterations (`-count`) since single runs are noisy. Beware the compiler optimising away unused results.

**Fuzzing.** Go has native fuzzing (Go 1.18): `func FuzzXxx(f *testing.F)` with `f.Add` seeds and `f.Fuzz(func(t *testing.T, in string){...})`, run with `go test -fuzz=FuzzXxx`. Failing inputs are saved under `testdata/fuzz` and become regression tests. Best for parsers, decoders and anything handling untrusted input; assert properties (no panic, round-trip equality), not specific outputs.

**Other practices.**

- `go test -race ./...` in CI always (chapter 20).
- `go test -cover` and `-coverprofile` with `go tool cover`. Coverage is a signal, not a goal.
- `-count=1` bypasses the test result cache; `-run` filters by regex; `-short` and build tags separate slow integration tests; `-v` shows names; `-shuffle=on` randomises test order to expose hidden dependencies.
- `TestMain` for package-level setup. `testdata/` directories are ignored by the build and hold fixtures; golden files are common for large outputs.
- Test behaviour through exported APIs when you can (`package foo_test` for black-box tests).
- Avoid `time.Sleep` for synchronisation. Inject clocks or use channels and `Eventually`-style polling with a deadline.
- Design for testability: pass dependencies in, accept interfaces, take a `context`, keep `main` thin.

### Tools to master

| Concept | Tools | Target level |

## 20. Race detector, profiling and debugging

**In plain words:** The race detector finds data races while your tests run. A profiler (`pprof`) [a tool that measures where time and memory go] shows why a service is slow. Use these tools before you guess.

### Understand

**Race detector.** `go test -race ./...`, `go run -race`, or `go build -race`. It instruments memory accesses and reports data races **that actually occur during the run**, with the two conflicting stacks. It finds no race in code paths your tests never exercise. It has substantial CPU and memory overhead (several times), so use it in tests, CI and staging or a canary, not usually in full production. A clean race run is necessary but not sufficient: it cannot prove absence of races. Treat each report as a real bug.

**pprof.** Go's built-in sampling profiler. Expose it with `import _ "net/http/pprof"`, which registers handlers on `http.DefaultServeMux`. If your service uses its own mux, register the handlers explicitly and serve them on a separate, internal-only listener. Never expose them publicly: they leak internals and a CPU profile adds load.

Common profiles:

| Profile | Question it answers |
|---|---|
| `profile` (CPU) | Where is CPU time spent? |
| `heap` | What holds memory now (`inuse_space`) and what allocated it (`alloc_space`)? |
| `allocs` | Which code allocates most, driving GC pressure? |
| `goroutine` | What are all goroutines doing, and are they piling up? |
| `block` | Where do goroutines wait on channels and sync (needs `runtime.SetBlockProfileRate`)? |
| `mutex` | Which locks are contended (needs `runtime.SetMutexProfileFraction`)? |
| `trace` | Scheduler and latency timeline (`go tool trace`) |

Typical use:

```
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
go tool pprof http://localhost:6060/debug/pprof/heap
go tool pprof -http=:8081 cpu.pprof      # interactive web UI with flame graph
(pprof) top
(pprof) list FuncName
```

Reading it: **flat** is time in the function itself, **cum** includes callees. Look for a wide frame in the flame graph. Profile under realistic load, over long enough to collect samples, and compare two profiles with `-base`. In benchmarks use `go test -bench . -cpuprofile cpu.out -memprofile mem.out`. Remember that wall-time stalls (waiting on the database) show up in `block` or traces, not in a CPU profile. Profile-guided optimisation (PGO) lets the compiler use a CPU profile. It is supported from Go 1.20 and on by default (`-pgo=auto`) from Go 1.21: `go build` uses a `default.pgo` file in the main package directory if present.

**Diagnosing a goroutine pile-up.** Fetch `/debug/pprof/goroutine?debug=2`, find the large groups of identical stacks, and read the line where they block (for example `chan send`, `select`, `semacquire`, `IO wait`). That line identifies the missing cancellation or the stuck dependency.

**Debugging.** `dlv` (Delve) is the Go debugger: `dlv debug`, `dlv test`, `dlv attach <pid>`, `dlv exec ./bin`, with breakpoints, goroutine inspection (`goroutines`, `goroutine <n>`) and stack views. In containers it requires ptrace permission and a build without optimisation (`-gcflags="all=-N -l"`). In production, prefer logs, metrics, traces and pprof to attaching a debugger. Send `SIGQUIT` to a Go process to dump all goroutine stacks and exit (be careful in production). `GOTRACEBACK=all` prints all goroutines on crash.

**Static analysis in CI.** `go vet`, `staticcheck`, `golangci-lint` (which bundles many linters such as `errcheck`, `govet`, `staticcheck`, `ineffassign`, `gosec`), `govulncheck`. Pin the linter version and agree on the enabled set so the output is stable.

**Observability in services.** Structured logs with request IDs, RED metrics (rate, errors, duration) per endpoint, and distributed tracing with OpenTelemetry. Export `runtime` metrics (goroutines, heap, GC pause) and `db.Stats()`. Profiles answer "why" after metrics say "what".

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Races | `go test -race`, `go build -race` | Reproduce, read and fix a race report |
| CPU and memory profiling | `net/http/pprof`, `go tool pprof`, flame graph, `-base` diffs | Find a hot function and an allocation hog |
| Contention and goroutines | pprof `goroutine`, `block`, `mutex` | Explain a pile-up from the stacks |
| Timeline | `runtime/trace`, `go tool trace` | Know when a trace beats a profile |
| Debugger | `dlv debug`, `dlv attach`, `dlv test` | Set breakpoints and inspect goroutines |
| Linting | `go vet`, `staticcheck`, `golangci-lint`, `govulncheck` | Keep CI clean and understand each class of finding |
| Runtime logs | `GODEBUG=gctrace=1`, `schedtrace`, `GOTRACEBACK` | Read GC and scheduler diagnostics |

### Common mistakes

- Skipping `-race` because tests are "slow".
- Exposing pprof on a public port.
- Profiling an idle process, or reading a CPU profile to diagnose time spent waiting on I/O.
- Optimising a function that is a small fraction of total time.
- Attaching a debugger to a production process during an incident without a plan.
- Disabling a linter rule rather than understanding the finding.

### Self-check

- How do you find why goroutine count grows steadily in production?
- What is the difference between `flat` and `cum` in pprof?
- Which profile shows lock contention, and what must you enable first?

## 21. Go versus Node for backend services

**In plain words:** Both Go and Node can build good backend services. Go often suits CPU work and many connections. Node often suits JavaScript teams and thin I/O-bound services. Choose by workload and team, and measure.

### Understand

Both are excellent for network services. The choice depends on workload, team and operational needs, not fashion.

| Dimension | Go | Node.js |
|---|---|---|
| Concurrency model | Goroutines on a multi-threaded scheduler; blocking-style code | Single-threaded event loop; async I/O; worker threads or processes for CPU |
| CPU-bound work | Runs in parallel across cores without blocking other requests | Blocks the event loop; needs workers, a pool or a separate service |
| Typing | Static, compiled, simple type system | Dynamic, with TypeScript adding static checks that are erased at runtime |
| Error handling | Returned values, explicit | Exceptions and promise rejections |
| Deployment | One static binary, small image, fast start | Runtime plus dependencies; larger images; startup includes module loading |
| Memory footprint | Low per request; predictable | Higher baseline; V8 heap limits apply |
| Latency tails | Low and steady; GC pauses are short | Event-loop stalls from synchronous work or GC affect all requests |
| Ecosystem | Strong stdlib; smaller but solid third-party set; strong in infrastructure, networking, CLIs | Vast package ecosystem; strongest for web, full-stack JS, tooling |
| Shared types with frontend | None | Same language and shareable types and validation |
| Iteration speed | Fast compile; more boilerplate | Very fast prototyping; rich frameworks |
| Observability and profiling | pprof and trace built in | Good tooling (inspector, clinic, flame graphs) but more external |
| Hiring and familiarity | Smaller pool in some markets | Very large pool |

**Choose Go when:**
- The service is performance- or concurrency-sensitive: high connection counts, proxies, gateways, streaming, queue consumers, data pipelines.
- You need predictable latency and low memory, or CPU work alongside I/O in the same process.
- You are building infrastructure: CLIs, agents, controllers, network services.
- You want simple deployment, few dependencies and long-term maintainability across many engineers.

**Choose Node when:**
- The team is JavaScript-first and the service is a thin, I/O-bound layer (a BFF, an API aggregator, server-side rendering).
- Sharing code, types and validation with a TypeScript frontend is valuable.
- Time to first version matters most and the workload is modest.
- The ecosystem you need (a particular SDK or framework) is strongest in JavaScript.

**Honest caveats.** Node is fast enough for most CRUD APIs: the database, not the language, is the bottleneck. A badly written Go service (leaks, unbounded goroutines, missing timeouts) fails worse than a simple Node one. Migration for performance rarely pays off before measurement identifies the language or runtime as the constraint. Mixed estates are common: Go for hot-path services and workers, Node or TypeScript for product-facing APIs.

**Mental translations from Node.**

| Node idea | Go equivalent |
|---|---|
| `async/await`, promises | Goroutines and blocking calls; channels for results |
| `Promise.all` | `errgroup` or `WaitGroup` |
| `AbortController` | `context.Context` |
| Express middleware | `func(http.Handler) http.Handler` |
| `process.on('SIGTERM')` | `signal.NotifyContext` and `Server.Shutdown` |
| npm and `package.json` | Go modules and `go.mod` |
| `JSON.parse` to any object | `json.Unmarshal` into typed structs |
| Cluster or pm2 for all cores | One process uses all cores |
| Unhandled rejection handler | `recover` at goroutine and handler boundaries |

### Tools to master

| Concept | Tools | Target level |
|---|---|---|
| Decision making | load tests (`k6`, `wrk`, `hey`, `vegeta`), profiles | Justify a choice with measurements |
| Interop | gRPC, protobuf, OpenAPI, HTTP/JSON | Run Go and Node services together with clear contracts |

### Common mistakes

- Choosing a language for benchmark headlines rather than workload and team.
- Rewriting a working service without profiling it first.
- Writing Node-style code in Go (callback chains, `any` everywhere) or Go-style code in Node.

### Self-check

- Give two workloads where Go is clearly better and two where Node is a reasonable choice.
- What does the Node event loop prevent that Go's scheduler allows?
- What operational advantages does a static binary give?

## 22. Practice labs

**In plain words:** These labs are small exercises. Each one has a goal and a clear "done" condition. Try each one before you search for answers.

Do these on a machine with a recent Go toolchain. Each states the goal and what "done" looks like. Attempt before looking anything up.

1. **Toolchain tour.** Create a module with two packages and a `cmd/` binary. Run `gofmt`, `go vet`, `go test ./...`, `go mod tidy`. Cross-compile for Linux with `CGO_ENABLED=0` and inspect the result with `file`. Done: a static binary under 20 MB that runs in a `scratch` container.
2. **Slice aliasing.** Write a program that demonstrates two slices sharing memory after `append`, then fix it with `slices.Clone` and a full slice expression. Print `len` and `cap` at each step and predict them first.
3. **Nil-interface trap.** Reproduce the typed-nil error bug, write a test that catches it, and fix it.
4. **Error design.** Build a small `orders` package with a sentinel `ErrNotFound` and a typed `ValidationError`. Write an HTTP error mapper using `errors.Is` and `errors.As`. Test wrapped errors across three layers.
5. **Concurrent map crash.** Write a map shared by goroutines without a lock, run with `-race`, read the report, fix it with `RWMutex`, then benchmark `Mutex` versus `RWMutex` versus `sync.Map` for your read-to-write ratio.
6. **Worker pool.** Process 10,000 jobs with N workers, context cancellation and first-error stop using `errgroup`. Verify no goroutines remain with `goleak`.
7. **Leak hunt.** Write a function with a timeout and an unbuffered result channel that leaks. Show the leak in `/debug/pprof/goroutine?debug=2`, fix it two ways, and add a leak test.
8. **Pipeline.** Build a three-stage pipeline (generate, transform, aggregate) where cancelling the context stops all stages promptly. Prove it with a test.
9. **Production-grade server.** Write an HTTP service with the four server timeouts, a recover middleware, request-ID middleware, `slog` logging, `/healthz` and `/readyz`, and graceful shutdown on `SIGTERM`. Prove with `curl` and a slow request that in-flight work finishes before exit and that new connections are refused.
10. **HTTP client behaviour.** Call a slow `httptest.NewServer` with a client timeout and a context deadline. Demonstrate connection reuse with and without draining the body, observing connection counts.
11. **JSON edge cases.** Write tests showing unexported fields, `omitempty`, absent versus zero (pointer field), large integers through `any`, nil versus empty slices, and `DisallowUnknownFields`.
12. **Pool exhaustion.** With a local PostgreSQL (or any SQL database), set `SetMaxOpenConns(2)`, run slow queries concurrently, and watch `db.Stats()` `WaitCount` and request latency. Then deliberately forget `rows.Close()` and observe the leak.
13. **Transactions.** Implement a money-transfer function with `BeginTx`, `defer Rollback`, and a failure midway. Test that nothing is committed, and that mixing `db` and `tx` breaks atomicity.
14. **Test suite.** For one package, write table-driven tests, an `httptest` handler test, a fuzz test for a parser, and a benchmark with `-benchmem`. Compare two implementations with `benchstat`.
15. **Profile an incident.** Take a deliberately slow service (an accidental O(n squared) loop, excessive allocation, a hot lock). Use CPU, allocs and mutex profiles to find each. Write the before and after numbers.
16. **GC and memory limit.** Run an allocation-heavy program under `GODEBUG=gctrace=1` with different `GOGC` values and a `GOMEMLIMIT`, inside a container with a memory limit. Explain each change in GC frequency and RSS.
17. **CI pipeline.** Configure CI to run `gofmt` check, `go vet`, `staticcheck` or `golangci-lint`, `govulncheck`, `go test -race -cover ./...` and a build. Done: a deliberately introduced race and a vet finding both fail the pipeline.
18. **Port a Node endpoint.** Take an Express endpoint that calls two APIs and a database in parallel and reimplement it in Go with `errgroup`, timeouts and typed JSON. Load test both and write up where they differ and why.

### Model answers (condensed)

**1.** A goroutine is a function executing concurrently, scheduled by the Go runtime onto OS threads. It has a small, growable stack and is cheap to create, so very many can exist. OS threads are heavier and scheduled by the kernel. When a goroutine blocks, the runtime runs another on the thread.

**2.** Every variable starts as its type's zero value: 0, `false`, `""`, `nil` for pointers, slices, maps, channels, functions and interfaces. Good types make the zero value usable (`sync.Mutex`, `bytes.Buffer`), avoiding constructors. The downside is that you cannot tell "unset" from "zero" without a pointer or a dedicated type.

**3.** An array has a fixed length that is part of its type and is copied by value. A slice is a header (pointer, length, capacity) over an underlying array, and copying it shares the elements.

**4.** `len` is the number of elements in the slice; `cap` is the number of elements from the slice's start to the end of its underlying array, which is how many can be appended without reallocation.

**5.** Functions return an `error` as a value, and callers check `if err != nil` and handle or wrap it. There are no exceptions for normal failures, so failure paths are visible. `panic` and `recover` exist for unrecoverable programmer errors.

**6.** `defer` runs a call when the surrounding function returns. Deferred calls run last-in first-out. Arguments are evaluated at the `defer` statement. It is used for unlocking, closing and cleanup.

**7.** Unbuffered: send and receive rendezvous, so the send blocks until a receiver is ready. Buffered: a send blocks only when the buffer is full, a receive only when empty. Unbuffered synchronises; buffered decouples with limited queueing.

**8.** A pointer receiver `(t *T)` receives the address, so it can mutate the value and avoids copying. Use it when the method mutates, the struct is large, or it contains a mutex. Be consistent across the type's methods.

**9.** Implicitly: a type satisfies an interface if it has all its methods. There is no declaration. The method set matters: a value of `T` has only value-receiver methods, while `*T` has both.

**10.** `gofmt` is the canonical formatter. It removes style debates and noisy diffs, and is run on save and in CI. `goimports` additionally fixes imports.

**11.** The order is unspecified and randomised between iterations. Never depend on it. Collect and sort the keys when you need deterministic output.

**12.** It adds missing module requirements and removes unused ones so `go.mod` and `go.sum` match the code. Run it before committing.

**13.** If `len < cap`, `append` writes into the existing array and returns a slice sharing it, so other slices over that array see the change. If the capacity is exceeded, it allocates a larger array, copies, and the result no longer aliases the old one. You cannot assume either, so clone or limit capacity (`s[a:b:b]`) when aliasing would be harmful, and always use the returned slice.

**14.** An interface value holds a type and a value; it is nil only if both are nil. If a function has return type `error` and returns a nil `*MyErr`, the interface has type `*MyErr` and is not nil, so `err != nil` is true. Fix by returning literal `nil` on success and not returning typed pointers as interfaces.

**15.** `%w` in `fmt.Errorf` wraps an error, preserving the chain. `errors.Is(err, target)` checks whether any error in the chain equals the target (sentinels). `errors.As(err, &t)` finds the first error in the chain assignable to the type of `t` and sets it (typed errors with data).

**16.** Two goroutines access the same memory concurrently, at least one writes, with no synchronisation ordering them. Consequences are corruption and crashes. Detect with `go test -race` (or `-race` builds), which reports races that occur during execution. Fix with mutexes, channels or atomics.

**17.** It carries cancellation, deadlines and request-scoped values across API boundaries. Conventions: first parameter named `ctx`, do not store it in structs, always call `cancel`, derive children from a parent, use `WithValue` only for request-scoped data with unexported key types, and pass it to every blocking call.

**18.** Receiving from a closed channel yields remaining buffered values and then zero values with `ok == false`. Sending to a closed channel panics, as does closing a closed or nil channel. Only the sender should close, and only when receivers need a completion signal.

**19.** Start N goroutines reading from a jobs channel and selecting on `ctx.Done()`. The producer closes the channel when finished. Use `errgroup.WithContext` to wait and to cancel on the first error, and `SetLimit` to cap concurrency. Make sure sends also respect cancellation.

**20.** Construct an `http.Server` with `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` and `IdleTimeout`, a body size limit, recover and logging middleware. Without timeouts, slow or malicious clients hold connections and goroutines indefinitely.

**21.** Use `signal.NotifyContext` for `SIGTERM`, then call `srv.Shutdown(ctx)` with a bounded timeout shorter than the orchestrator's grace period. It stops accepting connections and waits for in-flight requests. `ListenAndServe` returns `http.ErrServerClosed`, which is expected. Fail readiness first so the load balancer drains.

**22.** An unclosed body keeps the connection from returning to the pool and leaks resources; draining it to EOF lets the connection be reused. `http.Client` owns a connection pool, so creating one per request defeats keep-alive. Also set a timeout, since the default client has none.

**23.** `*sql.DB` is a pool that opens connections lazily. Key settings: `SetMaxOpenConns` (cap, default unlimited), `SetMaxIdleConns` (default 2), `SetConnMaxLifetime`, `SetConnMaxIdleTime`. When the cap is reached callers block, so latency rises while the database looks idle. Monitor `db.Stats()`.

**24.** A slice of cases with names, inputs and expectations, run with `t.Run`. For handlers, build a request with `httptest.NewRequest`, call `ServeHTTP` with an `httptest.NewRecorder`, and assert on status and body. Use `httptest.NewServer` for client tests.

**25.** Numbers decode as `float64`, so integers above 2^53 lose precision. Use typed structs, `Decoder.UseNumber`, or transport large IDs as strings.

**26.** Use a mutex to protect shared state such as caches, counters and registries, and when several fields change together. Use channels to transfer ownership, build pipelines, signal events and coordinate lifecycles. Pick the simpler one.

**27.** Before Go 1.22 a `for` loop shared one variable across iterations, so closures and goroutines could all see the last value. From Go 1.22, per-iteration variables are the default, selected by the `go` version in `go.mod`. Passing the value as an argument works in every version.

**28.** Use pointer fields, `sql.Null*` types, or custom types: in JSON a `*int` is nil when absent, in SQL a nullable column maps to `sql.NullInt64` or a pointer. For PATCH semantics also consider a wrapper type that records presence.

**29.** Notice rising goroutine count in metrics. Fetch `/debug/pprof/goroutine?debug=2` and group identical stacks to find where they block (channel send, receive, lock, I/O). Typical causes are missing cancellation or an unbuffered result channel after a timeout. Fix with context, buffered channels or `select`, and add `goleak` tests and an alert on goroutine count.

**30.** The scheduler multiplexes goroutines (G) on threads (M) holding a processor (P). When a goroutine blocks on network I/O, the runtime parks it using the netpoller and runs other goroutines on that thread. On a blocking syscall, the P is handed off to another thread so other goroutines continue. This is why blocking-style code scales.

**31.** The compiler decides whether a value can stay on the stack or must go to the heap, based on whether it can prove the value does not outlive the function. Heap allocation adds GC cost, so escape-driven allocations on hot paths hurt tail latency. Inspect with `-gcflags=-m`, measure with benchmarks and `-benchmem`, and optimise only when profiles justify it.

**32.** A concurrent tri-colour mark-and-sweep collector with short stop-the-world phases, not compacting. Cost scales with live heap and allocation rate. `GOGC` controls how much the heap grows before the next cycle (higher means more memory, less CPU). `GOMEMLIMIT` sets a soft memory ceiling so the collector works harder near it, useful under container limits.

**33.** Correlate with metrics (GC, goroutines, pool wait, saturation). Take CPU, allocs, `block` and `mutex` profiles and a trace during the spike. Check GC logs (`gctrace`), pool `WaitDuration`, downstream latencies and lock contention. Compare against a baseline profile. Fix the specific cause, such as allocation churn, a hot lock, or pool starvation.

**34.** Compare live heap (`heap` profile `inuse_space` over time, `runtime/metrics`) rather than RSS alone. A sawtooth that returns to a baseline is normal GC behaviour; a rising baseline is retention. Diff two heap profiles with `-base` to find growing allocation sites, and look for unbounded maps, caches, goroutine leaks, sub-slice retention and un-stopped tickers.

**35.** Use `errgroup.WithContext` with `SetLimit`, a per-call timeout derived from the request context, and results written to indexed slots or a mutex-guarded structure. For partial-failure policy, decide per dependency whether failure is fatal (return the error and cancel siblings) or optional (record, continue, degrade), and do not use `errgroup` first-error semantics for optional calls. Add retries only for idempotent calls with backoff and jitter.

**36.** The repository translates driver errors to domain errors (`ErrNotFound`, `ErrConflict`) and wraps with context. The service adds business meaning and decides which to expose. The transport layer maps domain errors to status codes and safe messages in one place, and logs unexpected errors once with request ID. Use `errors.Is` and `errors.As` throughout.

**37.** It defines the conditions under which a read observes a write: happens-before relations created by channels, mutexes, `WaitGroup`, `Once`, atomics and goroutine creation. Without such ordering, the compiler and CPU may reorder or cache accesses, so unsynchronised flags can be read stale forever and values can tear. A race is undefined in practice, not merely slow or imprecise.

**38.** Decide from the workload (CPU versus I/O, concurrency and latency needs), team skills, ecosystem needs, deployment constraints, and shared code with the frontend, then validate with a measurement. Go for concurrency-heavy, latency-sensitive or infrastructure services and simple deployment; Node for thin I/O-bound APIs and JavaScript-first teams sharing types with the frontend.

**39.** Take the database's connection limit, subtract headroom for admin and migrations, divide by the maximum number of instances (including during rolling deploys and autoscaling) to get `MaxOpenConns` per instance. Set idle connections near that for steady traffic, set lifetimes for failover, and consider a pooler such as PgBouncer. Verify with `db.Stats()` and database-side connection metrics.

**40.** Thin `main` that wires dependencies explicitly; domain packages with no framework imports; small consumer-defined interfaces; context on all blocking calls; errors translated at boundaries; configuration validated at startup; hand-written fakes plus real-database integration tests; table-driven unit tests; `-race` and lint in CI; no global mutable state.

**41.** Interfaces give runtime polymorphism and fit behaviour contracts (`io.Reader`). Generics give compile-time reuse across types without boxing or type assertions and fit containers and slice or map helpers. Overusing generics adds complexity; overusing `any` loses type safety. Prefer the simplest concrete code and generalise when duplication is real.

**42.** `gofmt` check, `go vet`, `staticcheck` or `golangci-lint`, `govulncheck`, `go test -race -cover ./...`, build of a static binary, integration tests against a real database, a `go mod tidy` diff check, container image build and scan, and optionally benchmark comparison and fuzz seed regression.

## 25. Glossary

**In plain words:** this table explains the hardest words in the guide in simple language. Return here when a term is unclear.

| Term | Plain meaning |
|---|---|
| Goroutine | A function running at the same time as others, managed by the Go runtime. |
| Scheduler | The runtime part that decides which goroutine runs on which thread. |
| GOMAXPROCS | The number of goroutines that can run Go code at the same moment. |
| Channel | A typed pipe that goroutines use to pass values to each other. |
| Buffered channel | A channel with a small queue, so a send does not wait for a receiver until the queue is full. |
| Data race | Two goroutines use the same memory at the same time, and one writes, with no coordination. |
| Mutex | A lock that lets only one goroutine use shared data at a time. |
| Atomic | An operation on one value that cannot be interrupted halfway. |
| Happens-before | A rule that guarantees one step is finished and visible before another step starts. |
| Context | A value passed down calls that carries cancel signals, deadlines and request data. |
| Goroutine leak | A goroutine that never ends and keeps its memory forever. |
| Slice | A view of part of an array: a pointer, a length and a capacity. |
| Capacity | How many elements a slice can hold before Go must allocate a new array. |
| Zero value | The default value of a variable that you did not set. |
| Rune | A Unicode character stored as a number (an int32). |
| Interface | A list of methods; any type that has them satisfies it. |
| Method set | The methods that a type has for the purpose of satisfying interfaces. |
| Embedding | Putting one type inside another so its fields and methods are available directly. |
| Sentinel error | A fixed error value, such as `ErrNotFound`, that callers compare against. |
| Escape analysis | A compiler check that decides if a value lives on the stack or the heap. |
| Garbage collector (GC) | The runtime part that frees memory that is no longer used. |
| Live heap | The memory that the program still uses and the GC cannot free. |
| Stop-the-world pause | A very short moment when the GC pauses all goroutines. |
| Graceful shutdown | Stopping a server after it finishes the requests already in progress. |
| Connection pool | A set of open connections that are reused instead of opened for each request. |
| Slowloris | An attack where a client sends data very slowly to keep a connection open. |
| Profiling (pprof) | Measuring where a program spends CPU time or memory. |
| Flame graph | A chart of a profile where wider boxes mean more time spent. |
| Fuzzing | Testing with many generated random inputs to find crashes. |
| Generics | Code written once that works with several types. |
